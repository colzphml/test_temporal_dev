# test_temporal_dev — эксперимент «Temporal vs чистый Python» для ИИ-агентов

Измеряем, что ИИ-агент разрабатывает быстрее: один и тот же интеграционный флоу
на **Temporal (Python SDK)** или на **чистом Python (asyncio)**. Стенд полностью
переносим: docker compose + make, единственные требования — Docker Desktop,
make, Python ≥ 3.10 (brew python@3.13 подходит).

## Быстрый старт

```bash
make up        # поднять Temporal + моки бизнес-сервисов (первый раз качает ~1 ГБ)
make selftest  # самопроверка стенда эталонными решениями (~3 мин)
```

Дальше — протокол эксперимента в [EXPERIMENT.md](EXPERIMENT.md).

## Что здесь есть

```
docker-compose.yml   стенд: Temporal (auto-setup + postgres + ui + admin-tools) и моки
mocks/               моки бизнес-сервисов (FastAPI) + чекер инвариантов (судья)
spec/                задание: SPEC.md (общая часть) + вариантные части + шаблоны воркспейса
scripts/             харнесс: preflight, wait_ready, workspace, verify, timer, selftest
reference/           эталонные решения обоих вариантов — только для селфтеста стенда
runs/                воркспейсы прогонов (генерируются, в git не попадают)
results/             замеры времени, отчёты, архив решений
```

## Как устроен эксперимент (кратко)

1. Агент-испытуемый получает воркспейс `runs/<вариант>/` с заданием `TASK.md`,
   готовым venv и командой `make verify`.
2. TASK.md собирается из **общей** спецификации (`spec/SPEC.md`) и **вариантной**
   части (`spec/variant_*.md`). Стартовый промпт обеих сессий идентичен —
   различие вариантов только внутри воркспейса.
3. Задание: провести 10 заказов через флоу «резерв → оплата → доставка →
   уведомление» поверх нарочно ненадёжных мок-сервисов. В сценариях зашиты:
   временные 500 (ретраи), отказ банка и out-of-stock (компенсации/saga),
   потерянный ответ платёжки (идемпотентность), провал доставки (refund),
   медленная доставка (конкурентность: пересечение интервалов обработки,
   мягкий лимит 90с).
4. `make verify` — единственный критерий готовности: сбрасывает моки, запускает
   решение, прогоняет чекер инвариантов. Таймер фиксирует время от `make begin`
   до первого зелёного verify.

## Мок-сервисы

Один FastAPI-контейнер (порт 8100) с четырьмя логическими сервисами: склад,
платежи, доставка, уведомления. Поведение детерминировано (`mocks/app/scenarios.py`):
сбои привязаны к order_id и счётчикам попыток, поэтому прогоны воспроизводимы.
Журнал всех вызовов — `GET /admin/state`, `GET /admin/ledger`; сброс —
`POST /admin/reset`. Чекер (`mocks/app/checker.py`) живёт в том же процессе
и оценивает журнал: `GET /admin/check`.

## Ключевые решения и почему

- **REST-моки вместо Kafka.** Кафка добавила бы вес стенду и клиентские
  библиотеки обоим вариантам, но ничего не дала бы сравнению «оркестрация vs
  ручной код». Возможное продолжение — триггер заказов из топика (фаза 2).
- **Детерминированные сбои вместо random.** Иначе результаты прогонов
  несравнимы, а чекер не может требовать конкретных ретраев.
- **Чекер в контейнере моков, а не на хосте.** У него общая память с моками
  (журнал), на хосте не нужны зависимости, и он одинаков для обоих вариантов.
- **Зависимости предустановлены в venv воркспейса.** Меряем скорость
  разработки, а не скорость pip и Wi-Fi. Пины: `temporalio==1.31.0`,
  `httpx==0.28.1`.
- **Требования на живучесть при рестарте воркера в задание не входят.** Это
  главный козырь Temporal, но честная реализация в чистом питоне раздула бы
  вариант B на порядок. Вынесено в идеи второй серии (см. EXPERIMENT.md).
- **Эталоны в `reference/`.** Стенд самопроверяется (`make selftest`): эталоны
  проходят, испорченные версии (нет refund, новый Idempotency-Key на каждую
  попытку) чекер ловит. В прогоны эксперимента заглядывать туда нельзя.

## Отладка стенда

- `make ps`, `make logs` — статус и логи контейнеров.
- `make clean && make up` — полный пересбор с чистой базой.
- Порт занят — `preflight` предупредит; посмотреть кем: `lsof -nP -iTCP:8100`.
- Селфтест оставляет воркспейсы чистыми; перед прогоном всё равно пересоздай:
  `make workspace VARIANT=... FORCE=1`.
