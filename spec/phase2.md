# Дополнение (фаза 2): живучесть при убийстве процесса

Все требования фазы 1 остаются в силе. Сверху добавляется одно:

1. В разгаре обработки (после нескольких успешных списаний) харнесс жёстко
   убивает ВЕСЬ процесс решения — SIGKILL, без предупреждения и без шанса
   что-то дозаписать. Через ~1 секунду он запускает `solution/run.sh` заново.
2. Повторный запуск обязан довести ВСЕ заказы до правильных терминальных
   состояний, НЕ дублируя побочные эффекты: по-прежнему ровно одно списание
   на заказ, ровно один возврат при провале доставки, никаких лишних
   отправлений. Чекер проверяет всё то же, что в фазе 1, плюс то, что после
   разрыва работа реально продолжилась и завершилась.
3. Контракт run.sh расширяется: скрипт могут запускать несколько раз подряд.
   Каждый запуск означает «доведи всё до конца»: что уже сделано — не
   переделывать, либо переделывать безопасно (идемпотентно).
4. В окружении обоих запусков есть переменная `RUN_ID` — одинаковая для обоих
   запусков внутри одного verify и разная между разными verify. Используй её
   там, где нужен стабильный идентификатор прогона, переживающий рестарт
   процесса.
5. Повторное финальное уведомление с тем же статусом допустимо (at-least-once);
   уведомления с противоречивыми статусами — провал.

Ключевая мысль фазы: побочные эффекты во внешних сервисах должны быть привязаны
к стабильным идентификаторам (заказ + прогон), а не к случайным значениям,
рождающимся заново при каждом старте процесса.
